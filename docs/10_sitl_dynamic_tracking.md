# M0-C5B1 SITL Dynamic Line Tracking

M0-C5B1 is a PX4 v1.14.3 SITL-only experiment for smooth horizontal line
tracking. It must not be used with real flight hardware.

## Safety Boundary

The experiment entry point is:

```bash
scripts/experiments/m0_c5b1_sitl_line.sh
```

The script refuses to continue unless `UAV_ALLOW_SITL_FLIGHT=YES` is present.
Before any `/mavros/set_mode` or `/mavros/cmd/arming` service call, it checks:

- PX4 is exactly tag `v1.14.3`;
- PX4 commit is `1dacb4cdef2d7145754fc788fa8dc482eed74b40`;
- the running PX4 process includes `build/px4_sitl_default/bin/px4`;
- Gazebo Classic `gzserver` is running;
- `/mavros/fcu_url` starts with `udp://`;
- `/mavros/fcu_url` does not contain `serial://` or `/dev/tty`;
- no `/dev/ttyACM*` or `/dev/ttyUSB*` device is present.

If an abnormal condition occurs while armed, the script requests `AUTO.LAND`.
It does not force disarm in the air.

## Trajectory

The project launch file is:

```bash
roslaunch uav_bringup m0_c5b1_line_tracking.launch
```

This launch starts the state bridge, `trajectory_preview_node`, and
`offboard_adapter_node`. PX4, MAVROS, and the one-shot dynamic trajectory
publisher are started only by the guarded experiment script.

The trajectory is generated by the M0-C5A C++ dynamic trajectory generator. The
experiment script passes the latest valid `/uav/state` pose as parameters and
does not duplicate the trajectory mathematics.

M0-C5B1-R1 uses a two-stage trajectory protocol. Stage A publishes an
independent 60 second ground-hold trajectory:

```text
x = current_x
y = current_y
z = current_z
yaw = current_yaw
velocity = acceleration = 0
```

That hold trajectory is used only for setpoint prestream, OFFBOARD switching,
and arming. The takeoff and line trajectory is not generated until
`armed=true` has been confirmed.

Stage B rereads the latest valid `/uav/state`, generates the dynamic flight
trajectory from that pose, and publishes it with
`Trajectory.header.stamp = now + 1.0 s`. During this one second handoff the
old ground-hold setpoint remains active. `trajectory_preview_node` therefore
queues a valid future-start trajectory as pending while continuing to sample
the current active trajectory; the pending trajectory is promoted atomically
when its `header.stamp` is reached. The script verifies that the new trajectory
is valid, the `trajectory_id` changed, the first point is continuous with the
current target, and the first velocity and acceleration are zero.

The flight sequence is:

```text
(x0, y0, z0)
-> 1 s initial hold
-> 5 s smooth climb to (x0, y0, z0 + 1.0)
-> 2 s center hold at altitude
-> 5 s smooth line to (x0 + 1.0, y0, z0 + 1.0)
-> 5 s smooth line to (x0 - 1.0, y0, z0 + 1.0)
-> 5 s smooth line to (x0, y0, z0 + 1.0)
-> 10 s hover
-> AUTO.LAND
-> final armed=false
```

The climb and line segments use the same fifth-order scalar time law documented
in `docs/09_dynamic_trajectory_baseline.md`; segment endpoints have zero
velocity and acceleration. Yaw is fixed to the starting yaw from `/uav/state`.

## Control Order

After the ground-hold trajectory is published and preview/offboard-adapter
health is confirmed, the script:

1. opens the runtime output gate;
2. verifies at least 2 seconds of setpoint prestream;
3. rejects prestream frequency below 20 Hz;
4. requests `OFFBOARD`;
5. waits for actual `mode=OFFBOARD`;
6. requests arming;
7. waits for actual `armed=true`;
8. confirms the active target is still the ground hold;
9. publishes the dynamic flight trajectory;
10. monitors tracking until the line and hover are complete;
11. requests `AUTO.LAND`;
12. waits for automatic disarm;
13. confirms final `armed=false`;
14. closes the runtime output gate.

Service calls are limited to a small retry count and are not called at high
frequency.

## Monitoring And Metrics

Runtime monitoring covers MAVROS connection, armed state, mode, `/uav/state`
freshness, adapter status, setpoint rate, target/actual position and velocity,
roll, pitch, NaN/Inf, horizontal error, height error, and unexpected OFFBOARD
exit.

Safety aborts are separate from performance acceptance. Safety aborts protect
the flight envelope: connection loss, stale state, adapter `FAULT`, setpoint
rate below 10 Hz, unexpected OFFBOARD exit, NaN/Inf, sustained horizontal
envelope violation, actual height overshoot above target, actual height below
the start envelope, sustained height error, or roll/pitch above 30 degrees.
Height tracking error uses `abort_height_error_m=0.9` with
`abort_height_error_dwell_sec=1.0`, so a single transient sample does not abort
the run. Actual overshoot above target uses the harder
`abort_height_overshoot_m=0.5` envelope.

Performance acceptance is computed only over `LINE_FORWARD`, `LINE_REVERSE`,
`LINE_RETURN`, and `CENTER_HOLD`. `PREFLIGHT`, `OFFBOARD_PREARM`, climb,
landing, and disarmed data are reported separately and are not mixed into the
line tracking RMS.

The run directory is:

```text
/tmp/uav_m0_c5b1/run_<timestamp>/
```

It contains rosbag data, node logs, `summary.json`, `tracking_samples.csv`, and
`tracking_metrics.json`. Bags, ULog files, db3 files, and logs stay outside Git.

The script reuses:

```bash
scripts/analysis/trajectory_tracking_metrics.py
```

Metrics include setpoint frequency, OFFBOARD and arming confirmation time,
coverage, 3D position RMS error, horizontal RMS/max error, height mean/RMS
error, velocity RMS error, maximum actual speed and acceleration, turnpoint
errors, center endpoint error, abnormal intervals, NaN/Inf count, adapter FAULT
count, unexpected OFFBOARD exit count, and AUTO.LAND-to-disarm time.

## Failed First Run And R1 Fix

The first M0-C5B1 attempt is preserved as:

```text
/tmp/uav_m0_c5b1/run_20260727_195543
```

It passed the safety chain, entered OFFBOARD, armed, requested `AUTO.LAND` on
abort, and ended with `armed=false`. It did not pass tracking acceptance. The
run aborted during climb on sustained height error around `0.720 m`, before
`LINE_FORWARD`, `LINE_REVERSE`, `LINE_RETURN`, or `CENTER_HOLD` were reached.

Offline replay of `summary.json`, `tracking_metrics.json`, and `m0_c5b1.bag`
showed:

- `trajectory_stamp -> output_gate`: about `0.063 s`;
- `trajectory_stamp -> OFFBOARD confirm`: about `2.822 s`;
- `trajectory_stamp -> arm confirm`: about `3.823 s`;
- at arming confirmation, target height offset from start was effectively
  `0.0 m`;
- actual liftoff occurred about `7.800 s` after arming, when target height had
  already advanced about `0.871 m`;
- climb phase height RMS was about `0.537 m` with maximum absolute height error
  about `0.847 m`;
- line tracking phases were `not_reached`.

The evidence does not indicate an ENU z sign error. The primary classification
is `CLIMB_PROFILE_TOO_AGGRESSIVE` / `VERTICAL_CONTROL_TRACKING` for the actual
SITL takeoff response, plus `ABORT_RULE_NOT_PHASE_AWARE` because the first
implementation mixed climb transient behavior with horizontal-line tracking
acceptance. R1 fixes this with the two-stage trajectory protocol, explicit
phase topic `/uav/experiment_phase`, phase timestamps in `summary.json`, and
phase-aware metrics.

The first R1 re-run is preserved as:

```text
/tmp/uav_m0_c5b1/run_20260727_202230
```

It validated the SITL chain, entered OFFBOARD, armed, switched to the generated
flight trajectory, requested `AUTO.LAND` on abort, and ended with
`armed=false`. It did not reach climb or line tracking. Logs showed that the
flight trajectory was accepted before its future `header.stamp`, causing the
adapter to report `trajectory has not started` and the experiment to abort on
setpoint frequency below 10 Hz. The follow-up code fix is the pending handoff
behavior described above; no second R1 flight was executed after that fix.

## First-Run Acceptance

The first M0-C5B1 line tracking run is accepted only if:

```text
setpoint average frequency >= 20 Hz
data coverage >= 95%
horizontal RMS error <= 0.25 m
maximum horizontal error <= 0.5 m
height RMS error <= 0.25 m
center endpoint error <= 0.25 m
NaN/Inf count == 0
adapter FAULT count == 0
unexpected OFFBOARD exit count == 0
final armed=false
```

This stage does not execute circle tracking, figure-eight tracking, stream-loss
tests, obstacle simulation, or real aircraft flight.
